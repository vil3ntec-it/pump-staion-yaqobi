# VILL3N Sync v1 — نیمهٔ برنامهٔ کامپیوتر

بندِ ۲۰ی پرامپت (پروتکل) و بندهای ۱ تا ۱۴ی بخشِ ۲۲ (برنامهٔ دسکتاپ)،
همان‌طور که در `native/` پیاده شد. سمتِ سرور از قبل آماده بود و دست نخورد؛
شرحش در ریپوی `shop`: `docs/SYNC-v1-fa.md` و `docs/LOGIN-fa.md`.

> ⚠️ **این سند هم می‌گوید چه چیزی ساخته نشد و چرا.** هر انحراف از متنِ
> پرامپت این‌جا با دلیلش نوشته شده. «ساخته شد»ِ دروغ در این ریپو ممنوع است.

---

## ۰. نقشه، در یک نگاه

```
کاربر چیزی می‌نویسد
   │
   ▼  PumpDbContext.SaveChanges()  ← تنها نقطهٔ نوشتن
داده + یک ردیفِ `SyncOps`   (همان تراکنش)
   │
   ▼  PumpDbContext.Saved ⇒ SyncEngine.Nudge()   (مکثِ ۵۰۰ms)
POST /api/sync/v1/push   دسته‌ای، حداکثر ۲۰۰ op
   │
   ├─ applied/duplicate ⇒ روی دستگاه `Synced = true`
   ├─ rejected(reason)  ⇒ دیگر فرستاده نمی‌شود، دلیلش می‌ماند
   └─ 426               ⇒ **نگه داشته می‌شود** تا سرور به‌روز شود

هر ۳۰ ثانیه، یا با پیامِ `changed` از wss:
GET /api/sync/v1/pull?since=<cursor>  ⇒ SQLِ خام روی دفترِ محلی
```

## ۱. دفترِ تغییرات (Oplog) — و «یک نقطه»ی بندِ ۱

**`PumpDbContext.Stamp()`** تنها جایی است که op ساخته می‌شود، و این عمدی
است.

برنامه از پیش سی‌وچند سرویسِ داده دارد (`DebtorService`،
`LedgerService`، `WaraqDataService`، …) و همه‌شان سرِ آخر به یک جا
می‌رسند: `SaveChanges`. پس «Repositoryِ واحد»ِ پرامپت **همان‌جا**ست، نه
یک لایهٔ تازهٔ موازی. اگر فردا سرویسِ سی‌وسومی نوشته شود، بی این‌که کسی
چیزی یادش بماند opهایش نوشته می‌شوند.

- op و خودِ داده در **یک تراکنش** می‌نشینند (`SyncOps.AddRange` پیش از
  `base.SaveChanges()`): یا هر دو، یا هیچ‌کدام.
- `update` فقط فیلدهای **عوض‌شده** را دارد (`PropertyEntry.IsModified`).
- `delete` هیچ فیلدی ندارد — بدنه‌اش زیرِ یک کیلوبایت است و آزمون دارد.
- چهار جدول هیچ‌وقت نمی‌روند: `AppUser` · `Setting` · `TrashItem` ·
  `AuditEntry` — همان چهارتایی که فهرستِ سفیدِ سرور هم ندارد.
- نوشتنِ **خام** op نمی‌سازد، و این هم عمدی است: تنها جای نوشتنِ خام،
  اعمالِ opهای **رسیده** است. اگر آن‌ها op می‌ساختند، هر تغییرِ دستگاهِ
  دیگر دوباره به سرور برمی‌گشت — پژواکِ بی‌پایان.

فایل‌ها: `PumpYaqobi.Persistence/OpLog.cs` · `PumpDbContext.cs` ·
`PumpYaqobi.Domain/Entities/SyncEntities.cs`.

## ۲. شناسه‌ها — ⚠️ **انحرافِ عمدی از بندِ ۲**

بندِ ۲ می‌گوید: «همهٔ Primary Keyها به ULID (String)، با Migration که
شناسه‌های عددی قدیمی را نگاشت کند.»

**این کار نشد، و نباید بشود.** به‌جایش هر ردیف یک ستونِ تازه گرفت:

```csharp
public abstract class EntityBase
{
    public long    Id      { get; set; }   // دست‌نخورده
    public string? SyncUid { get; set; }   // ← تازه: شناسهٔ همگام‌سازی
}
```

### چرا

۱. **دیتابیسِ زنده، پنج سالِ یک پمپِ واقعی.** بازنویسیِ کلیدِ اصلیِ
   سی‌وهفت جدول یعنی بازسازیِ همهٔ کلیدهای خارجی (`DebtorId`،
   `FuelAccountId`، `MoneyAccountId`، `AccountId`، `SourcePurchaseId`، …)
   در یک مهاجرتِ یک‌طرفه. همان جایی است که داده گم می‌شود، و برگرداندنش
   ممکن نیست.

۲. **مهاجرتِ افزایشی برگشت‌پذیر است.** `ALTER TABLE … ADD COLUMN` در
   SQLite جدول را بازنویسی نمی‌کند و لحظه‌ای است؛ و اگر روزی بخواهیم پسش
   بگیریم، فقط یک ستونِ بی‌مصرف می‌ماند. بازنویسیِ کلید برگشت ندارد.

۳. **مشکلی که بندِ ۲ می‌خواست حل کند، حل شده است.** خطرِ واقعیِ کلیدِ
   خودافزا «تصادمِ دو دستگاهِ آفلاین» است: هر دو ردیفِ ۵۰۰۱ می‌سازند و
   روی سرور یکی می‌شوند. با `SyncUid`، هویتِ ردیف در همگام‌سازی همان
   رشتهٔ یکتاست و `Id` فقط شمارهٔ داخلیِ همین کامپیوتر می‌ماند. سرور
   `Id` را اصلاً نمی‌بیند.

### پر کردنِ ردیف‌های قدیمی

ردیف‌های **تازه** ULIDِ واقعی می‌گیرند (`PumpYaqobi.Domain/Ulid.cs`،
بی هیچ بستهٔ تازه‌ای، و در یک میلی‌ثانیه هم تکراری نمی‌سازد).

ردیف‌های **قدیمی** با **یک** `UPDATE` برای هر جدول پر می‌شوند:

```sql
UPDATE "SafeEntries" SET "SyncUid" = '<ریشه>-' || "Id" WHERE "SyncUid" IS NULL;
```

`<ریشه>` یک ULIDِ یک‌بارساخته است که در `SyncState.UidSeed` می‌ماند و
**هیچ‌وقت عوض نمی‌شود**. نتیجه در جدول یکتاست (چون `Id` یکتاست) و میانِ
دستگاه‌ها هم (چون ریشه تصادفی و مالِ همین نصب است).

⚠️ این شناسه‌ها **مرتبِ زمانی نیستند** و لازم هم ندارند: ترتیب را
`server_seq`ِ سرور می‌گوید، نه شناسهٔ ردیف.

⛔ عوض کردنِ ریشه یعنی همان ردیف‌ها بارِ دوم با شناسهٔ دیگری به سرور
می‌روند — یعنی دفترِ سرور دو برابر. آزمونش:
`SyncOpLogTests.Risheye_Shenase_Yek_Bar_Sakhte_Mishavad`.

## ۳. موتورِ همگام‌سازی (بندِ ۳)

`PumpYaqobi.App/Services/SyncEngine.cs`

| خواسته | حال |
|---|---|
| Push دسته‌ای با Debounce ۵۰۰ms | ✅ `PumpDbContext.Saved ⇒ Nudge()`، سقفِ ۲۰۰ op |
| Pull با cursor | ✅ هر ۳۰ ثانیه یا با پیامِ `changed` |
| WSS live | ✅ `ClientWebSocket` روی `/api/sync/v1/live` |
| Backoff نمایی | ✅ ۲ · ۴ · ۸ … تا پنج دقیقه، بی‌نهایت تلاش |
| تشخیص آنلاین/آفلاین | ✅ از `CloudLink.Reach` که فقط از جوابِ واقعیِ سرور پر می‌شود |
| صف پس از بسته شدنِ برنامه | ✅ صف خودِ جدولِ `SyncOps` است |
| سرویسِ سیستم (اختیاریِ بندِ ۳) | ❌ **ساخته نشد** — پایین |

⛔ **«سرویسِ ویندوز برای خالی کردنِ صف وقتی برنامه بسته است» ساخته نشد**،
و این یک انحرافِ آگاهانه است: یک سرویسِ جدا یعنی یک نصب‌کنندهٔ تازه، یک
مسیرِ به‌روزرسانیِ تازه، و دو فرآیند که هم‌زمان روی یک فایلِ SQLite
می‌نویسند. خودِ پرامپت هم آن را «اختیاری» نوشته. صف هیچ‌وقت گم نمی‌شود،
فقط تا باز شدنِ بعدیِ برنامه صبر می‌کند.

### ترمزِ سرعت

قاعدهٔ همیشگیِ این ریپو: **کارِ دوره‌ای بی ترمزِ `Version` ممنوع.**

- حلقه با `PumpDbContext.Version` ترمز می‌گیرد: تا داده عوض نشده، صف خالی
  باشد و وقتِ pull نرسیده باشد، **حتی یک `SELECT`** هم نمی‌زند.
- `_lastVersion` در **پایانِ** هر دور دوباره خوانده می‌شود، وگرنه ذخیرهٔ
  خودِ حالِ همگام‌سازی، دورِ بعد را «داده عوض شد» می‌دید و حلقه تا ابد
  می‌چرخید.
- `SyncEngine.Disabled` در همهٔ آزمون‌ها و سنجه‌ها روشن است (`Program.cs`ِ
  `UiTests` و `Parallelism.cs`ِ `Tests`). بی آن، هر سنجه‌ای که پنجره
  می‌سازد به سرورِ **زندهٔ** اشتراک درخواست می‌زد — از رانرِ CI.

## ۴. ورود با کدِ شش‌رقمیِ ایمیلی (بندِ ۴)

مسیرها: `POST /api/auth/pump/request-code` · `GET …/request-status` ·
`POST …/verify` — همان قراردادِ ثابتِ `shop/server/src/routes/app-auth.js`.

- **درِ سوم، نه جانشین.** راهِ ایمیل‌ورمز و ثبت‌نامِ سه‌پله‌ای دست‌نخورده
  ماندند؛ مشتری‌های امروز با همان وارد می‌شوند. صفحهٔ ورود حالا سه دکمه
  دارد: «حساب می‌سازم» · «حساب دارم» · «کدِ ایمیلی».
- شش خانه با پرشِ خودکار، Paste (از هر خانه‌ای، همیشه از اول پخش
  می‌شود)، **ارقامِ فارسی و عربی**، ارسالِ خودکار پس از رقمِ ششم، و
  شمارشِ معکوسِ شصت ثانیه — عددش از `resend_after`ِ خودِ سرور، نه حدسِ ما.
- همهٔ تصمیم‌ها در `CodeBoxesViewModel` است و آزمون دارد؛ صفحه فقط فوکوس
  را جابه‌جا می‌کند.
- «ایمیل رفت یا نه؟» از `request-status`ِ خودِ سرور پرسیده می‌شود، نه
  حدس. اگر سرویسِ ایمیلِ سرور خراب باشد کاربر همان لحظه می‌فهمد.
- ⛔ پاسخِ `request-code` **همیشه** ۲۰۰ است مگر سقفِ نرخ، پس برنامه
  هیچ‌وقت نمی‌گوید «چنین حسابی نیست» — با آن می‌شد فهمید کدام ایمیل حساب
  دارد.
- توکن‌ها از همان راهِ همیشگی می‌نشینند: `SecretStore` ⇒ DPAPI روی
  ویندوز، AES-GCM جای دیگر. هیچ توکنی خام روی دیسک نیست.
- تازه‌سازیِ خودکار از قبل بود (`CloudLink.AccountAsync`) و دست نخورد.

## ۵. «اشتراکِ من» و تپش (بندِ ۵)

`GET /api/pump/heartbeat` هر پانزده دقیقه، از داخلِ همان حلقه.

⚠️ **انحرافِ کوچک و لازم**: خواستهٔ کار `GET /api/me/heartbeat` بود، ولی
آن مسیر `requireUser`ِ **دکان** دارد و به توکنِ پمپ «چنین نشستی نیست»
می‌دهد. مسیرِ درستِ این برنامه `/api/pump/heartbeat` است — **همان تابعِ
سرور** (`portal.heartbeatHandler`)، فقط با هویتِ بخشِ پمپ.

- عوض شدنِ پلن در پنل: آنلاین ⇒ همان لحظه؛ آفلاین ⇒ سرِ اولین اتصال.
- نتیجه در `AppSettings` کش می‌شود (`Entitlements.Remember`)، پس صفحهٔ
  اشتراک آفلاین هم چیزی برای نشان دادن دارد.
- ⛔ **هیچ عددِ قیمتی از این‌جا نمی‌آید و در کلاینت نوشته نشده.** قیمت فقط
  در صفحهٔ پلن‌ها و فقط از سرور.

## ۶. اعلان‌ها (بندِ ۶)

- بنرِ داخلِ برنامه: نوارِ پایینِ پنجره (`MainViewModel.NoticeText`).
- اعلانِ خودِ ویندوز: `NativeNotice.cs` — `Shell_NotifyIcon` با P/Invoke،
  **بی هیچ بستهٔ تازه‌ای**، همان راهی که `WaveRecorder` با `winmm` رفت.
- هر دو از **یک** جا می‌آیند (`SyncEngine.NoticeArrived`). قاعدهٔ جدا
  ننویسید، وگرنه روزی یکی می‌آید و آن یکی نه.
- روی غیرِ ویندوز، اعلانِ سیستمی بی‌صدا رد می‌شود و بنر تنها راهِ خبر است.

⚠️ **انحراف**: پرامپت «از WebSocket» می‌گوید. سوکتِ Sync v1 عمداً فقط
`{event:"changed", cursor}` می‌فرستد و خودِ سرور هیچ اعلانی از آن در
نمی‌دهد. پس اعلان از تپش می‌آید (و تپش با هر پیامِ `changed` هم زودتر
می‌دود). نتیجه برای کاربر یکی است؛ راهش با آن‌چه سرور واقعاً دارد جور شد.

⛔ **هیچ سرویسِ پولی و هیچ FCMی در کار نیست** — همان قاعدهٔ ریپو.

## ۷. قفلِ نرم (بندِ ۸)

`PumpYaqobi.App/Services/SoftLock.cs` + یک قلاب در
`PermissionService.ReadOnlyHook`.

```
دیدنِ همهٔ بخش‌ها      ✅ همیشه
چاپ و PDF و بکاپ      ✅ همیشه
چتِ پشتیبانی          ✅ همیشه
همگام‌سازی            ✅ همیشه
نوشتنِ تازه           🔒 تا تمدید
```

⛔ هیچ داده‌ای پاک یا پنهان نمی‌شود. و ارفاقِ چهارده‌روزهٔ
`Entitlements.Grace` جلوتر است، پس نرسیدن به سرور کسی را قفل نمی‌کند.

⚠️ **امروز اصلاً روشن نمی‌شود**، چون `Entitlements.Unlocked` به خواستهٔ
صریحِ صاحب ریپو `true` است. این کار آن یک خط را **دست نزد**: همان که
`false` شود، قفلِ نرم هم به کار می‌افتد. تا آن روز `SoftLock.ReadOnly`
همیشه دروغ است و `SoftLock.Banner()` خالی.

## ۸. Snapshot و پشتیبانِ رمزشده (بندِ ۹)

- `GET /api/sync/v1/snapshot` (با `Accept-Encoding: gzip`؛ فرستندهٔ
  همگام‌سازی رمزگشاییِ خودکار دارد و مهلتش دو دقیقه است).
- «بازیابی از سرور» در **تنظیمات ← همگام‌سازی**. ⛔ **هیچ ردیفی پاک
  نمی‌شود**: آن‌چه روی سرور هست می‌نشیند، و ردیفی که فقط این‌جاست دست
  نمی‌خورد. پاک کردن بر اساسِ «روی سرور نبود» یعنی یک خطای شبکه = دفترِ
  خالی.
- پشتیبانِ رمزشدهٔ محلی: `SyncBackup.cs` — `VACUUM INTO` و بعد AES-GCM با
  کلیدی که از همین کامپیوتر مشتق می‌شود و **هیچ‌جا ذخیره نمی‌شود**.
  فایلِ دست‌خورده بی‌صدا باز نمی‌شود.
- **پیش از مهاجرت، خودکار**: `PumpDbFactory.PatchSyncUid` نخست یک نسخهٔ
  `pre-sync` می‌گیرد، و فقط وقتی واقعاً مهاجرتی در پیش است.
- ⚠️ دفترِ بزرگ‌تر از ۲۵۶ مگابایت رمز نمی‌شود و همان نسخهٔ سالمِ
  `VACUUM INTO` می‌ماند: رمزگذاریِ AES-GCMِ دات‌نت کلِ بایت‌ها را یک‌جا
  می‌خواهد و نیم‌گیگ دفتر یعنی نزدیک یک‌و‌نیم گیگ رم، درست سرِ بالا آمدنِ
  برنامه.

## ۹. چراغِ نوارِ پایین (بندِ ۱۳)

سبز = همگام · زرد = در صف · خاکستری = بند نشده · سرخ = سرور خطا داد.

⛔ **هیچ نام و نشانیِ سروری در آن نوشته نمی‌شود** — همان قاعدهٔ دو چراغِ
سربرگ (سرورِ خانگی و سرورِ حساب). دلیل فقط در `ToolTip` است، و کلیک یعنی
«الان همگام کن».

⚠️ نوار بیرونِ `ScrollViewer` و `VerticalAlignment="Bottom"` است — همان
الگوی نوارِ بخش‌ها که بالای صفحه می‌ایستد؛ آوالونیا `position:sticky`
ندارد. `StatusGap` به همان بلندی جا باز می‌کند تا تهِ محتوا زیرش پنهان
نشود.

## ۱۰. تنظیمات (بندِ ۱۱) — ⚠️ **انحرافِ عمدی**

صفحهٔ «تنظیمات ← 🔄 همگام‌سازی»: صف، آخرین رفت‌وآمدِ موفق، خطای آخر،
نسخهٔ Schema، «الان همگام کن»، پشتیبانِ رمزشده، بازیابی از سرور، و
کلیدِ گزارشِ خطا.

⛔ **کادرِ نشانیِ سرور ساخته نشد.** بندِ ۱۱ آن را می‌خواهد («آدرس سرور با
تأیید رمز») ولی قاعدهٔ خودِ صاحب ریپو جلوتر است و `CloudAddressLockTests`
هر کادری را قدغن کرده: نشانی در `CloudConfig.BaseUrl` قفل است، چون اگر
از تنظیمات خوانده می‌شد هر کسی برنامه را به سرورِ خودش می‌برد، مجوزِ
خودش را امضا می‌کرد و قفلِ اشتراک با یک کادرِ متنی دور می‌خورد.

گزارشِ خطا (`POST /api/errors`، بندِ ۲۰٫۸) پیش‌فرض **روشن** است و از همان
صفحه خاموش می‌شود. فقط پیام، نوعِ استثنا و ردپای کوتاه می‌رود؛ خودِ سرور
هم هر چیزی شبیهِ ایمیل و شماره و توکن را می‌پوشاند.

## ۱۱. نسخهٔ Schema (بندِ ۲۰٫۶)

`OpLog.SchemaVersion = 1` — همان عددی که سرور برای بخشِ `pump` دارد
(`sync-v1-migrations.js`).

- برنامهٔ **قدیمی‌تر**: سرور خودش بالا می‌بردشان و `upgrade_available`
  می‌دهد.
- برنامهٔ **جدیدتر**: `426`، و ⛔ **هیچ opی دور ریخته نمی‌شود** —
  `SyncState.Holding` روشن می‌شود، چراغ زرد می‌ماند و دلیلش گفته می‌شود.
  هر دور یک opِ تکی محک می‌زند که سرور به‌روز شده یا نه.

⛔ هر جدول یا فیلدِ تازه = یک پله بالاتر **این‌جا و روی سرور**، با همان
شماره. جلو بردنِ یک‌طرفه یعنی ایستادنِ کلِ همگام‌سازی.

## ۱۲. اثرِ انگشت (`hash`) — ⚠️ فرستاده نمی‌شود

سرور `hash` را **اختیاری** گرفته و ناجورش کلِ op را رد می‌کند
(`hash_mismatch`). اثرِ انگشتِ سرور روی `JSON.stringify`ِ جاوااسکریپت
گرفته می‌شود و شکلِ عددِ اعشاری در دو زبان مو‌به‌مو یکی نیست. پس فرستادنش
فقط ریسکِ **دادهٔ گم‌شده** بود.

هش محلی محاسبه و روی ردیفِ `SyncOps` نگه داشته می‌شود، برای سلامتِ خودِ
دفتر.

## ۱۶. این دفتر مالِ کدام حساب است — `SyncStateRow.AccountId`

افزوده‌شده در ۱۴۰۵/۰۷/۰۷، پس از خواستهٔ صریحِ صاحب ریپو: «برای افتتاحِ حساب
نباید اطلاعات همه حذف یا از سر یا ریست بشن… و همون اطلاعاتی که اول بی حساب
داشت توی حسابِ جدیدش بیاد.»

```
بی‌حساب ⇒ حسابِ تازه      AccountId خالی بود ⇒ فقط ثبت ⇒ «بارِ اول» همه را می‌برد
بی‌حساب ⇒ حسابِ از قبل    همان، به‌علاوهٔ pull با cursor صفر ⇒ ادغام
حسابِ A ⇒ حسابِ B        AccountId عوض شد ⇒ BindTo دفتر را از نو می‌بندد
```

`SyncStore.BindTo(accountId)` تنها جای تصمیم است و `SyncEngine.StepAsync`
**پیش از** `SeedStep` صدایش می‌زند. سه کاری که می‌کند و چرایشان، و پنج
قاعده‌ای که نباید بشکنند، در `CLAUDE.md` (بخشِ «افتتاحِ حساب هیچ چیزی را از
سر نمی‌کند») نوشته شده — این‌جا فقط سرِ خط:

- ⛔ یک بیت از دفتر لمس نمی‌شود؛ فقط `SyncOps` و ردیفِ حال.
- ⛔ `UidSeed` عوض نمی‌شود (بخشِ «شناسه‌ها»).
- ⛔ opهای حسابِ قبلی برداشته می‌شوند، ولی داده‌شان با «بارِ اول» دوباره
  می‌رود — این بار به حسابِ تازه.
- ⛔ `Cursor = 0` یعنی **ادغام**، نه جایگزینی.
- ⚠️ شناسهٔ خالی («نمی‌دانیم») هیچ چیزی را از نو نمی‌کند.

⚠️ ستونش در `PumpDbFactory.PatchColumns` هم نوشته شده — آن فهرست **دستی**
است. آزمون: `AccountDataCarryTests`.
